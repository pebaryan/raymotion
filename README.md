# raymotion

Remotion-style motion graphics / video engine — pure C++ on **raylib + ffmpeg**, no web
stack. Every visual and audio asset is generated by code (shapes, gradients, blobs,
text, keyframe/easing tracks, procedural WAV soundtrack); nothing loads binary media.

## Build (this machine)

Configure with `tools/configure.sh` (it pins the MSVC compiler, llvm rc/mt substitutes,
and the library search dirs this stripped VS install needs):

```sh
sh tools/configure.sh          # cmake + ninja -> build/raymotion.exe
```

### Why the extra vendoring under third_party/

This machine's Visual Studio 2022 install keeps its C runtime headers and import
libraries inside **Windows Kits** (`C:\Program Files (x86)\Windows Kits\10\...`) rather
than merged into the VC-tools trees, and those directory names contain spaces which
poison raw `link.exe` command lines. So we vendor space-free mirrors:

| mirror | source | purpose |
|---|---|---|
| `third_party/msvc-sdk-libs` | Windows Kits `Lib\10.0.22621.0\um\x64` real MSVC import libs (kernel32, user32, gdi32, winmm, ddraw, ...) | system DLL imports |
| `third_party/msvc-crt` | Kits `Lib\...\ucrt\x64` + VS `lib\x64` selected archives | UCRT import archive (`ucrt.lib`) |
| `third_party/vs-libs` | VS `VC/Tools/MSVC/<v>/lib/x64` (all *.lib) | DLL-runtime glue (`msvcrt`, `vcruntime`, `msvcprt`, `oldnames`, delayimp) |
| `third_party/raylib` | official raylib 6.2 win64 MSVC pack | vendored engine lib |
| `third_party/c-headers`, patched `raylib.h` stdarg fallback | (legacy backup) | only used if Kits include dir is absent; primary path uses the real Kits ucrt headers via `/I` |

Import-lib gotchas learned here (kept in `tools/mkimports.py` for regeneration from raw
DLL exports): bare-name def rows parse fine but mixing alias+plain forms in one archive
makes `LNK1127: library is corrupt`; hand-rolled aliases silently mismatch when the
real Windows-Kits archives exist — prefer copying the real `.LIB` files (bigger/smaller
size checks caught a bogus hand-built `winmm.lib` that broke raylib's `timeBeginPeriod`).

Everything links one CRT model, the DLL runtime (`/MD`: msvcrt + vcruntime + ucrt +
msvcprt), because the prebuilt `raylib.lib` is `/MD`. Don't add `libcmt`/`libvcruntime`
(static) or `ucrtd` (debug) to the link line. The exe needs the VC++ 2015-2022
redistributable (`VCRUNTIME140.dll`, `MSVCP140.dll`) at runtime.

The three Microsoft mirrors are machine-local and not redistributable; `.gitignore`
keeps them out of version control. `tools/configure.sh` and the import-lib scripts
locate the repo themselves; set `MSVC_DIR` (and `LLVM_MT`) to point at another
Visual Studio toolset.

`tools/bin/rc.exe` is a compiled shim (source `tools/shim_rc.c`): `link.exe` spawns
`rc.exe` for its manifest step and llvm-rc can't digest the emitted source, so the shim
writes an empty COFF object (we pass `/MANIFEST:NO` too — modern Windows embeds none).

## Usage

```
build/raymotion.exe list
build/raymotion.exe preview <name>                 # live window, esc quits
build/raymotion.exe render    <name> [--crf N] [--draft] [--no-music] [--png-frames]
build/raymotion.exe still     <name> --at FRAME [--png PATH]
```

* `render`: per-frame deterministic draw through the timeline tree from a
  composition-sized render texture, piped as raw RGBA straight into ffmpeg ->
  `out/<name>.mp4` (+ AAC soundtrack from the procedural synth for `music=1` comps; the
  WAV is written to `out/<name>_frames/track.wav`). `--png-frames` instead writes a PNG
  sequence `out/<name>_frames/fNNNNN.png` and needs no ffmpeg.
* ffmpeg lookup: `--ffmpeg PATH`, then `RAYMOTION_FFMPEG`, then any winget Gyan.FFmpeg
  install under `%LOCALAPPDATA%`, then `C:/Program Files/ffmpeg`, `C:/ffmpeg`, then `PATH`.
  Paths with spaces are fine.
* Rendering is frame-index driven (hash-based RNG per frame) => reproducible outputs.
* Capture uses the offscreen composition canvas, not the desktop framebuffer: a
  1920x1080 composition exports exactly 1920x1080 even if its preview window is clamped.
  `--draft` downsamples the entire canvas to half size (rounded down to even dimensions
  for yuv420p); it does not crop coordinates.
* `still` draws only the requested frame; frames carry no state, so it is identical to
  the same frame of a full render.
* Re-rendering clears only generated `f<digits>.png` files in the selected frame
  directory. ffmpeg is also capped to the requested frame count.
* `preview` closes with esc or the window's close button.
* `--png frame.png` and nested PNG paths both work. Failed exports return nonzero.

Compositions are registered in `src/scenes.cpp` (`register_scenes`).

### Here-and-There explainer

`build/raymotion.exe render here-there-explainer` generates a 108-second, 1280x720
caption-led introduction to Pedro Cabalar's treatment of HT and equilibrium logic,
with procedural diagrams and music. The author-hosted sources, chapter script and
scope notes are in `docs/here-there-explainer.md`. Worked examples are checked by
the `ht_semantics` CTest target.

(`%WINDIR%/Fonts/segoeui.ttf`) and refuse to fall back to raylib's bitmap font.

## Architecture

* `src/rmtn/timeline.hpp` — Remotion-like tree: nodes(start/duration), named easers,
  float/vec/color keyframe tracks, transform ctx, deterministic per-frame RNG.
* `src/rmtn/draw.hpp` — primitives (quads, gradient quads, roundRect, rings/arcs/sectors,
  stars, organic blobs, text) all transformed through the node ctx.
* `src/rmtn/synth.hpp` — sine-sum note events + envelopes -> WAV bytes, written for music.
* `src/scenes.cpp` — compositions registry (declarative tracks + lambda up/fn nodes).
* `src/fx_present.cpp` — tiered FX presentation renderer (fx-1..fx-4): FBO base capture,
  CPU readback bloom (threshold + separable blur at quarter-res), painter-lit 3D meshes,
  fullscreen grain/vignette/scanline/sparkle overlay shader. HUD is drawn after final
  composition. Render textures use flipped source rectangles when sampled; text in
  an FBO is not inherently mirrored. Shader uniform types are explicit.
  `fx-3-gpulit` is retained as a compatible CLI name, not a claim of GPU lighting.
* `src/main.cpp` — CLI (list/preview/render/still), shared drawTree() path for preview
  and render, ffmpeg discovery and raw-frame pipe.
* `src/ht_*.cpp` — Here-and-There explainer compositions; `rmtn/here_there.hpp` holds
  the executable two-atom HT semantics, `rmtn/ht_feed_layout.hpp` the feed's layout
  landmarks shared with its test.

Outputs verified on this host: `out/probe.mp4` (2.000 s, video), `out/demo-neon.mp4`
(7.500 s, video+audio aac), `out/demo-neon_still_0150.png`.


## Regression tests

Build and run `ctest --test-dir build --output-on-failure`.
The C++ renderer test uses a real OpenGL context and checks legacy dispatch, actual
GL uniform values, translucent glow, HUD visibility and repeat-frame determinism
for all four tiers. The Python CLI suite uses only the standard library plus
ffmpeg/ffprobe on PATH: it checks bare PNG paths, exact canvas dimensions, whole-frame
draft scaling and a real MP4 render with a deliberately planted stale frame.
Tests write isolated artifacts under `build/`, not the shipped `out/` media.
